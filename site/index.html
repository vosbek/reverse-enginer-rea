How it works

One read-only pass, five kinds of answer

You point Clearbox at a folder. A sealed workspace reads files without following links or leaving the folder. Analyzers turn those bytes into facts, a template picks the questions, and the report shows every answer with its source.

What a report gives you

Answers you can check line by line

Each template is a set of questions. These are real reports Clearbox produced, linked so you can open them.

Find a feature and get a plan to rebuild it

Describe a feature in plain words. Clearbox scores files by path, symbol names, and content, then follows the import graph to show how execution reaches it, what it depends on, and a leaves-first build order.

  • Import chains from entry points to the feature
  • Packages, settings, and host capabilities it needs
  • The existing tests that pin its behavior

Know what it can do to your machine before you run it

Documented rules flag process launches, network calls, file deletion, privilege requests, disabled TLS checks, unsafe deserialization, committed secrets (redacted in the report), and text that tries to instruct an AI agent.

  • Production code counted apart from tests and docs
  • Install-time scripts read from package manifests
  • Grouped by area of the codebase

Decode binaries from their headers

ELF, PE, Mach-O, WebAssembly, DEX, and archives are identified by their bytes. For Windows programs Clearbox reads the import table, version resource, signer names, hardening flags, and UTF-16 strings, then maps imported APIs to plain-language capabilities.

  • Who signed it, and what it says it is
  • What its imports let it do
  • URLs, paths, and object names it carries

See the architecture at a glance

Files are grouped into areas, and a matrix shows which areas import which. Load-bearing files, import cycles, and declared-versus-used dependencies come with it.

  • Python parsed with ast; JS/TS and Go imports resolved to files
  • Imports of build output mapped back to source
  • Dynamic imports listed as blind spots, not guessed

Safe by construction

Built to open code you don't trust

Reverse-engineering tools handle hostile input by definition. Clearbox's guarantees are enforced in code and checked by its tests.

Read-only jail

Files open read-only with O_NOFOLLOW. Paths outside the target and symlinks are refused. Reports can't be written inside the target.

No execution, no network

Python is parsed with ast, binaries with struct. A test fails the build if Clearbox imports subprocess or socket, or calls eval.

A ledger of every read

Each report lists every file it read with its SHA-256, plus a content hash that is identical on re-runs. Two reviewers can prove they saw the same thing.

Blind spots, stated

Dynamic imports, path aliases, oversized files, and other limits are listed on every report instead of being silently skipped.

Confidence on every view

Each result is labeled parsed, pattern, or heuristic, so you know which ones to double-check.

Agent-safe output

Over MCP, agents only see folders you allow. Text from the target is fenced with a random nonce so it can't pose as instructions.

Compared with REA

A safer first pass

REA is a capable, popular tool that drives decompilers and live programs. Clearbox does the parts that don't need to run anything, and does them with less to trust.

Get started

Python 3.11 and a folder

Clone or extract the target first. Clearbox never downloads anything for you, which keeps the network out of the picture.

Terminal
pip install git+https://github.com/vosbek/reverse-enginer-rea

clearbox scan ./some-app                     # architecture overview
clearbox scan ./some-app -t security-surface
clearbox scan ./installers -t binary-triage
clearbox trace ./some-app "search notes"     # feature trace
MCP config for your AI agent
{
  "mcpServers": {
    "clearbox": {
      "command": "clearbox",
      "args": ["mcp", "--allow-root", "/path/to/targets"]
    }
  }
}
