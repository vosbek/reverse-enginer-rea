How Clearbox works

Clearbox is about 3,200 lines of Python with no dependencies. It reads a folder through a single read-only workspace and turns the bytes into facts with eight analyzers. A template then chooses which questions the report answers, and every answer appears next to the lines it came from.

1. The workspace

Analyzers never open files themselves. Every read goes through the workspace, which applies the same rules each time and records the read in a ledger.

PropertyHow it is enforcedSource
Read-onlyFiles are opened with O_RDONLY | O_NOFOLLOW. Nothing in the target is ever written.workspace.py
Confined to the folderEach path is resolved with realpath and must lie under the target. Paths containing .., absolute paths and NUL bytes are refused.workspace.py
No symlinksThe directory walk records symlinks as skipped, and any read through one is refused.workspace.py
BoundedAt most 100,000 files, 4 MB per text file, 64 MB per binary and 2 GB in total. Anything over a limit is reported as a blind spot.workspace.py
No execution or networkA test parses Clearbox's own source and fails if it imports subprocess, socket, urllib, http or ctypes. It also fails if the code calls eval, exec, os.system or any file-deletion function.test_clearbox.py
Output kept apartThe command line refuses to write a report inside the folder being analyzed.cli.py
Credentials maskedA matched credential is reduced to its first four characters, its length and a SHA-256 fingerprint before any report sees it.risk.py

3. Templates

A report is defined by a template: a TOML file listing questions, each answered by one or more views. Clearbox runs only the analyzers those views need, in dependency order. A template that names an unknown view is rejected, and the error lists the valid ones.

Five templates are built in: overview, feature-trace, security-surface, dependency-audit and binary-triage. clearbox views lists every view available to custom templates.

handoff.toml, run with -t handoff.toml
id = "handoff"
name = "New-engineer handoff"
summary = "What a new teammate needs on day one."

[[sections]]
title = "Where do I start reading?"
question = "Entry points and the files everything depends on."
views = ["surface.entrypoints", "imports.hubs"]

[[sections]]
title = "What can break production?"
views = ["risk.summary", "surface.env"]

4. The evidence model

This is one finding from the REA scan, exactly as it appears in report.json. The HTML report shows the same record when its row is clicked, with a link to that line on GitHub.

Confidence states how the fact was established. It was either parsed from a real structure, matched by a documented pattern, or inferred heuristically.

Evidence pins the claim to a path, a line, the exact text, and the SHA-256 of the file as read.

The ledger at the end of each report lists every file read and the analyzers that used it. Its digest and a content hash of the report are printed at the top. The same input produces the same hashes.

Blind spots list what a run could not see, such as computed imports, path aliases, files over a limit, and the reach of pattern rules.

5. Use from an AI agent

Clearbox includes an MCP server with four read-only tools. It is started with --allow-root for each folder an agent may analyze, and every other path is refused. Custom template files are not accepted over MCP.

Text taken from the target is placed between <<<TARGET-DATA>>> markers that carry a fresh random nonce on every response. A file in the target therefore cannot forge the end of the fence and pass its contents off as instructions. The security template also flags text in the target that addresses an AI agent.

ToolPurpose
clearbox_templatesList templates and their parameters
clearbox_scanRun a built-in template and return the Markdown report
clearbox_traceRun a feature trace
clearbox_readReturn up to 400 lines of one file, to check evidence

6. What Clearbox does not do

  • Decompilation. Binary triage reads headers, imports and strings. Control flow and pseudocode require Ghidra, IDA or Hopper, ideally in a disposable virtual machine.
  • Runtime observation. Clearbox can show that code calls fetch. It cannot show which hosts that call reaches when the code runs.
  • Indirect calls. Pattern rules match literal call sites. A capability behind a wrapper is counted where the wrapper calls the real API.
  • Downloads. The target must already be on disk. Keeping the network out of the tool is deliberate.
