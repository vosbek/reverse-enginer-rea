How it works

Read everything, run nothing, show the source of every answer

Clearbox is about 3,200 lines of Python with no dependencies. A sealed workspace reads the target folder. Eight analyzers turn bytes into facts, a template chooses the questions, and the report shows each answer next to the lines it came from.

1 · The workspace

Every byte goes through one door

Analyzers never open files themselves. They ask the workspace, which applies the same rules to every read and writes each one into a ledger.

GuaranteeHow it's enforcedWhere
Read-onlyFiles are opened with O_RDONLY | O_NOFOLLOW. Nothing in the target is ever written.workspace.py
Stays in the folderEvery path is resolved with realpath and must sit under the target root. .., absolute paths and NUL bytes are refused.workspace.py
No symlinksThe directory walk records symlinks as skipped instead of following them, and a read through one is refused.workspace.py
BoundedAt most 100,000 files, 4 MB per text file, 64 MB per binary, and 2 GB in total. Anything over a limit becomes a blind spot.Limits
No execution, no networkA test parses Clearbox's own source and fails if it imports subprocess, socket, urllib, http, ctypes and similar modules, or calls eval, exec, os.system or file deletion.SelfAudit test
Output outside the targetThe command line refuses to write a report inside the folder it is analyzing.cli.py
Secrets redactedMatched credentials are reduced to their first four characters, a length, and a SHA-256 fingerprint before any report sees them.risk.py

3 · Templates

A report is a list of questions

Templates are TOML files. Each section asks a question and names the views that answer it. Clearbox runs only the analyzers those views need, in dependency order. A template that names a view that doesn't exist is rejected with a list of valid ones.

  • overview: architecture, weight, dependencies, entry points
  • feature-trace: where a feature lives and how to rebuild it
  • security-surface: what it can do to the host
  • dependency-audit: declared versus imported
  • binary-triage: formats, imports, signers, strings
handoff.toml · run with -t handoff.toml
id = "handoff"
name = "New-engineer handoff"
summary = "What a new teammate needs on day one."

[[sections]]
title = "Where do I start reading?"
question = "Entry points and the files everything depends on."
views = ["surface.entrypoints", "imports.hubs"]

[[sections]]
title = "What can break production?"
views = ["risk.summary", "surface.env"]
4 · Evidence

What a single finding carries

This is one real finding from the REA scan, exactly as it appears in report.json. The HTML report shows the same record when you click its row, with a link to that line on GitHub.

rea-security/report.json
{
  "rule": "priv.elevate",
  "title": "Requests elevated privileges",
  "severity": "high",
  "confidence": "pattern",
  "category": "privilege",
  "evidence": [{
    "path": "src/application/LinuxHopper.ts",
    "line": 337,
    "snippet": "const executable = isRoot ? command[0] : \"pkexec\";",
    "sha256": "b45f18669881fb28…12674f3"
  }],
  "tags": []
}

Confidence says how the fact was established: parsed from a real structure, matched by a documented pattern, or a heuristic inference.

Evidence pins the claim to a path, a line, the exact text, and the SHA-256 of the file as read. Anyone can check it against the same commit.

The ledger at the end of every report lists every file read and which analyzers used it. Its digest, plus a content hash of the whole report, is printed at the top. Same input, same hashes.

Blind spots list what the run could not see: computed imports, path aliases, files over a limit, and the reach of pattern rules.

5 · For AI agents

Four read-only tools over MCP

Agents are good at asking follow-up questions and bad at noticing when a file is trying to instruct them. Clearbox's agent interface is built around both facts.

ToolDoes
clearbox_templatesLists templates and their parameters
clearbox_scanRuns a built-in template on a folder and returns the Markdown report
clearbox_traceRuns a feature trace
clearbox_readReturns up to 400 lines of one file, to check evidence

Only folders you allow. The server starts with --allow-root for each folder; anything else is refused. Custom template files are not accepted over MCP.

Read-only by declaration. Every tool is marked read-only, non-destructive and closed-world.

Fenced output. Text from the target is wrapped between <<<TARGET-DATA 9f2c…>>> markers with a fresh random nonce each time, so a file can't fake the end of the fence and pose as instructions. The security template also flags text in the target that addresses an AI agent.

6 · Limits

What Clearbox does not do

1

No decompilation. Binary triage reads headers, imports and strings. Control flow and pseudocode need Ghidra, IDA or Hopper, ideally in a disposable VM.

2

No runtime behavior. Clearbox can show that code calls fetch, not which hosts it reaches when it runs.

3

Patterns see literal calls. A capability hidden behind a wrapper is counted where the wrapper calls the real API, not at every call site.

4

No downloads. You clone or extract the target yourself, which keeps the network out of the tool.
